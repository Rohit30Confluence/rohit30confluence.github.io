LogSentinel

What problem this solves

Apache access logs contain the evidence of most web-layer attacks — brute-force login attempts, injected SQL, reflected XSS, path traversal — but that evidence is only useful if it's parsed, decoded, and correlated as it arrives, not read after the fact. LogSentinel is built to sit in that gap: turning a raw, streaming log file into structured, rule-evaluated events in near real time.

How it works

Log lines are streamed and parsed incrementally rather than loaded in bulk, so the service can run continuously against a growing file. Each request is percent-decoded before rule evaluation, since encoded payloads are a common way attackers evade naive string matching. Detection rules run per request, and a per-IP history is kept so that isolated anomalies and repeated, escalating activity from the same source can be distinguished.

Engineering decisions

  • Streamed parsing rather than batch processing, so the analyzer scales with log volume instead of memory.
  • SQLite chosen for persistence to keep the service self-contained and easy to run without external infrastructure.
  • WebSocket alert streaming added alongside REST, so a dashboard can reflect detections live rather than polling.
  • CLI tooling and a traffic simulator built alongside the service to make detection rules testable without live traffic.

Security model

Detection is rule-based across four categories — brute force, SQL injection, XSS, and path traversal / LFI — with the percent-decoding step specifically added to reduce false negatives from encoded attack strings.

Testing & CI

Automated tests run in GitHub Actions across Python 3.10, 3.11, and 3.12, including an end-to-end check that exercises the CLI directly rather than only unit-level logic.

Where this stands

This is a personal, open-source project built to demonstrate detection engineering end to end — not a deployed production system with live traffic or measured outcomes. The GitHub repository has the full source and commit history.

What problem this solves

Most detection logic operates on structured data — but on the wire, everything starts as raw bytes. NDAP is a from-scratch attempt to own that whole chain in Rust: decode packets off the network, reconstruct the flows and streams they belong to, and only then apply detection logic — rather than relying on a higher-level library to do the hard networking part.

How it works

PCAP input is parsed and decoded layer by layer — Ethernet framing, then IPv4/IPv6, then TCP, UDP, or ARP — into typed structures the rest of the platform can reason about. Packets are grouped into flows using a 5-tuple (source/destination IP and port, plus protocol), and TCP streams are reassembled with basic out-of-order buffering so that detection isn't fooled by packets arriving out of sequence.

Engineering decisions

  • Structured as a Cargo workspace, splitting capture, decoding, flow tracking, detection, and API/CLI into separate modules rather than one monolithic binary.
  • Rust chosen deliberately for a packet-processing system where memory safety and predictable performance both matter.
  • axum and tokio used for the async API layer, keeping packet processing and the API surface decoupled.
  • Out-of-order buffering implemented for TCP reassembly rather than assuming a clean, in-order packet stream.

Security model

Detection rules operate on reconstructed flows and streams — not raw packets — covering port scans, SYN floods, and ARP spoofing, and were exercised against real packet captures rather than synthetic-only test data.

Where this stands

NDAP is an independent, open-source systems project, not a hardened or commercially deployed detection product. It's built to demonstrate the networking and Rust engineering underneath a detection platform. Source and history are on GitHub.
